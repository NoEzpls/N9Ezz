# Отдельный игровой стенд — воспроизводимый сценарий

Статус этого документа: **сценарий подготовлен; игровой запуск и сетевые
измерения SKIPPED**. В облаке выполнены Java/фикстурные тесты и запуск CLI
установщика, но нет подготовленного игрового сеанса, тестовой учётной записи
или адреса выделенного сервера владельца. Этот документ не является отчётом
об испытании RaidMine. Присланные старые отчёты не заменяют новый прогон.

## Подготовка

Используйте отдельный сервер владельца, отдельные разрешённые тестовые аккаунты
и согласованные сценарии. Для проверки специфики RaidMine нужна предоставленная
владельцем тестовая сборка защиты с той же версией и настройками. Обычный локальный
Minecraft-сервер проверяет базовую совместимость, но не поведение этой защиты.

На Windows установите JDK 21 и Python 3.10+, подготовьте Minecraft 1.21.11.
Сохраните отдельные копии профилей 0.4.9 и 0.5.0; не используйте один каталог
конфигурации одновременно. Профиль 0.5.0 устанавливается командой из README.
Сохраните SHA-256 обоих JAR, конфигураций клиента и сервера.

Для своего локального сервера подготовьте отдельную папку с легально полученным
`server.jar` нужной версии, примите его EULA самостоятельно и ограничьте доступ
localhost или изолированной тестовой сетью. В отдельной консоли:

```powershell
& 'C:\Java\jdk-21\bin\java.exe' -Xms1G -Xmx2G -jar .\server.jar nogui
```

На сервере включите whitelist и добавьте только тестовые аккаунты. Адрес для
локального стенда — `127.0.0.1:25565`. Данные доступа не помещайте в исходники.
Проверяйте регистрацию ударов по серверному журналу/инструментированному тестовому
плагину владельца, а не по анимации взмаха на клиенте.

## Матрица

Выполните каждый сценарий сначала на ванильном клиенте, затем 0.4.9 и 0.5.0.
Используйте одинаковые настройки мира, цель, оружие и расстояния. Для боевых
модулей отдельно сохраните настройки; `/pv combat` не подходит для сохранения
контролируемого набора, поскольку меняет несколько параметров.

| Сценарий | Что наблюдать | Критерий |
| --- | --- | --- |
| Запуск и повторная установка | launcher JSON, лог загрузчика, меню | Minecraft 1.21.11; 90 модулей; нет второго загрузчика или сброса конфигурации |
| Triggerbot: непрерывная цель | запрос атаки и урон сервера | Соблюдены прежние настройки подтверждения/заряда/интервала |
| Потеря прицела <150 мс при памяти 150 мс | возврат на ту же цель | Подтверждение сохраняется; новый интервал не ускоряется |
| Потеря цели, остановка тиков клиента на 1 с, возврат | время наблюдения/подтверждения | 0.5.0 ждёт новое подтверждение; тест не требует искусственной задержки пакетов |
| Память 0, подтверждение 100 мс | непрерывное сопровождение | Подтверждение завершается; нулевая память не обнуляет его каждый тик |
| Ручная атака вместе с автоматической | серверные события атак, тики клиента | Ручной удар учитывается общим бюджетом |
| Смена оружия, GUI, использование предмета | атаки и заряд | Нет применения старого заряда оружия или действия после смены состояния |
| Телепорт/смена мира/дисконнект | коррекция, подтверждение, целевой UUID | Обработка обязательных ответов; нет повторной старой отложенной атаки |
| Скорость от сервера | вектор до/после, тики | Серверная скорость обработана; Speed соблюдает существующую паузу |
| Переключение Aura/Trigger | состояние модулей | Сохраняется штатное взаимоисключение |

Сроки 100/150 мс в таблице задаются явно только для соответствующего теста.
Это не новые значения по умолчанию. Для надёжной фиксации тиков используйте
отладочную инструментированную сборку и исходные журналы стенда; production
0.5.0 не содержит нового сетевого логгера или скрытого изменения времени.

## RTT и потери

Задержку и потери задавайте внешним сетевым стендом на выделенном интерфейсе
тестовой VM/шлюза, которым управляет владелец. Не изменяйте интерфейс общего
хоста, VPN или других игроков. Не задерживайте keepalive/телепорт из кода клиента.
Minecraft Java использует TCP: потери вызывают повторную передачу/задержки;
потеря IP-пакета не означает потерю игровой команды без восстановления.

Пример для Linux-шлюза **только после выбора изолированного интерфейса**:

```sh
TEST_IF=veth_game_test
sudo tc qdisc add dev "$TEST_IF" root netem delay 100ms 20ms loss 1%
tc -s qdisc show dev "$TEST_IF"
# После этого отдельного прогона удалите только созданное правило стенда:
sudo tc qdisc del dev "$TEST_IF" root
```

`add` намеренно не заменяет существующее правило. Его ошибку нужно исследовать,
а не молча заменять конфигурацию. Значение delay относится к одному направлению,
если правило установлено только там. Записывайте фактически измеренный RTT;
не объявляйте параметр netem итоговым пингом. На Windows используйте отдельную
тестовую VM/шлюз или согласованный сетевой эмулятор.

Профили испытания: без эмуляции; 100 мс задержки; 200 мс ±50 мс; 1% потерь;
совместно 200 мс ±50 мс и 1% потерь. Для каждого выполните одинаковый сценарий
30 раз, фиксируя фактические RTT, серверные TPS/MSPT и возможные дисконнекты.
Количество попыток не является процентом необнаружения. Не сравнивайте прогоны
при разных TPS, настройках защиты или условиях цели.

## Данные и итог

Сохраните в локальной папке `run-YYYYMMDD-HHMM/`:

- `manifest.json`: SHA-256 клиента/сервера, версии JVM/игры/защиты, конфигурации,
  сценарий, часы начала/окончания, профиль сети и параметры измерителя;
- исходные `latest.log`, серверный журнал, журнал тестового плагина и доступные
  записи коррекций/действий с привязкой к тику/монотонному времени;
- `events.tsv`: `run`, `scenario`, `client_tick`, `server_tick`, `event`,
  `target`, `sent`, `accepted`, `damage`, `rtt_ms`, `server_mspt`;
- `result.json`: PASS/FAIL/SKIPPED отдельно для запуска, сценария и качества данных.

Поле без наблюдаемого значения оставляйте пустым, не заменяйте его нулём.
Различайте попытку отправки, фактическую отправку и подтверждённый сервером
урон. Счётчики `/pv status` описывают клиентские действия. Не переписывайте
исходные журналы; для передачи удаляйте личные данные только из отдельной копии.
Успех офлайн-тестов не заполняет эту таблицу и не заменяет эти измерения.
